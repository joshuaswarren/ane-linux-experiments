# 2026-10-01 jwm1 (T8103) macOS ADT capture: the ANE node carries preloaded firmware segments

Host: jwm1 (Apple M1 MacBookPro17,1), macOS 27.0 window (read-only ioreg; one reversible reboot, Omarchy left as default boot and verified afterwards; nothing touched USB/Type-C). Script: `mac-ane-adt.sh`. Node dump: `ane-dart-ane-adt-nodes.txt` (decoded from the full IODeviceTree plist; the 1.6 MB plist and the 17 MB AppleH11ANEInterface service dump are kept in the research notebook, not here).

## What the ADT says about the T8103 ANE
- `/arm-io/ane` (compatible `ane,t8020`, reg engine 0x26bc04000 + 32 MiB, second region 0x23b700000 + 0x8c000, interrupt 0x1a0, power-gates/clock-gates 0x12e, clock-ids 0x140/0x141/0x142, `ane-type` 4) has, besides the engine, the properties of a firmware-running coprocessor: **`pre-loaded` = 1, `segment-names` = `__TEXT;__DATA`, `segment-ranges` (two 32-byte records; raw bytes in the dump), `asc-dram-mask` = 0x0f000000 00, `uuid`, `function-mcc_dataset`**. iBoot therefore preloads an ANE firmware image into DRAM on T8103, in the same convention the other coprocessor nubs use. Segment records decode to physical bases 0x80093c000 (TEXT, size field 0xe4000) and 0x8015b4000 (DATA, size field 0x608000); treat the exact field layout as unverified (the M2/ANE lane owns that decode).
- There is no `iop-ane-nub` child: the ANE node itself is the firmware nub. (Other coprocessors here, aop/pmp/sep/sio/ans/smc/dcp/gfx-asc/acio, have `iop-*-nub` children.)
- `/arm-io/dart-ane`: DART instance 0x16, page size 0x4000, four 16 KiB register windows at 0x26b800000, 0x26b810000, 0x26b820000 and 0x26b804000, `bypass`, tunables for three instances; the Linux DT ane node has iommus already.
- No ANE firmware file exists on the macOS volume (`find /usr/standalone/firmware -iname '*ane*'` empty): the image is not a file, it is preloaded.
- Under the Linux boot the preloaded regions are not reserved: `/proc/iomem` reserves `asc-firmware@800b0c000` (0xa24000) and `asc-firmware@801b50000` (0x430000) for other coprocessors but not 0x80093c000-0x800a20000 or 0x8015b4000-0x801bbc000 (see `linux-iomem-asc.txt`), so by the time Linux runs the ANE image may have been overwritten. Whether m1n1 can dump it before handoff is untested.

## What this changes
The M2 agent's blocker list for a T8103 firmware boot (2026-10-01) had "T8103 needs its own H13 fw image; source and whether iBoot preloads it are unknown". Source answered: iBoot preloads it (ADT segments above). Still open: (1) the image must be captured before Linux overwrites it (m1n1 proxy dump, needs the USB link the M2 lane is using); (2) the T8103 static start sequence and the ASC mailbox/command transport, unknown; (3) the M1 host-driven driver writes TM registers that the running firmware must own; (4) whether the perf-mode message (CSNE_CMD 0x1f CH_PROPERTY_WRITE) is accepted. The ANE encoder gap (138-140 ms vs 113.27 ms, 0.81x) is not closed by this receipt; it removes one "unknown" from the route that could close it. No boot work was started.
