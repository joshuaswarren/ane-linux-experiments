## 1. Payload vs personalized wrapper — proven with the IPSW itself

`t602x_ane0_fw_selene_rc4x.im4p` (1,720,345 B) is a DER SEQUENCE:
`IA5 "IM4P" · IA5 "anef" · IA5 "1" · OCTET STRING(0x1a4000)` — the payload is
the raw arm64 Mach-O, **no IM4M/IM4R inside the file**. The per-device
personalization manifests live separately (`Firmware/Manifests/restore/…`),
and the TSS ticket is what the ECID binds. Three independent proofs that the
payload bytes are family-generic:

1. **BuildManifest cross-identity**: the ANE component carries ONE digest —
   `sha384 c63b638c2501…355dda` (of the whole im4p file; verified by
   recomputation) — shared by **24 BuildIdentities across 8 boards**
   (j180d, j414c, j414s, j416c, j416s, j474s, j475c, j475d = T6020/T6021/
   T6022, and every OS-flow variant of each). One byte sequence, many
   devices. `Personalize=true` is on all of them; it personalizes the
   signature envelope, not the image. (H13 styx shows the same shape: one
   digest, 6 boards.)
2. **Digest chain intact locally**: im4p `sha256 ad9151af4e73…` → payload
   `sha256 9f7915c431d288a2…` = byte-identical to the 2026-09-18 mined
   artifact (`fw-h14j-selene/*.macho`, recorded in `artifact-digests.txt`).
   `ipsw fw ane` decoded the payload without any device key — a device-
   wrapped image cannot do that.
3. **Runtime chip selection**: the payload itself selects per-chip tunables
   at run time ("Using T6020 A0 / T6021 A0 / T6021 B0 / T6021 B1 / T6022 …"
   in `H14TunableManager`, per the 2026-09-18 mined receipt §2), and the
   tunable tables are host-loaded (`CSNE_CMD_REG_FILE_LOAD`). A per-device
   image would not need a chip selector. (t602x_**ane1** is a genuinely
   different build — 570,512 bytes differ — an instance-specific build, not
   a device wrap; j414c uses ane0.)

**Conclusion: W11 §5's "Personalize=true, the image is device-entangled" is
disproven.** The firmware was never an external blocker; it was sitting in
this repo's own receipt artifacts.

## 2. Loading requirements — mined, not guessed

Image structure (parsed from the payload):

| datum | value | source |
| --- | --- | --- |
| type | `MH_PRELOAD` (filetype 5), arm64 | Mach-O header |
| segments | `__TEXT` vm `0x0` sz `0xe8000`; `__DATA` vm `0xe8000` vmsize `0x284000` (file `0xb8000` + zerofill); `__DATA_CONST` empty | LC_SEGMENT_64 |
| entry | **`LC_UNIXTHREAD pc = 0x0`** — linked at 0 | LC_UNIXTHREAD |
| internal boot state | `_rtk_boot_l1` (0x80) **all zero**; `_rtk_page_tables` (0x80000) **all zero**; `__sysvars` zero | section dump |
| `_fwinfo` | magic `0x1deafbabe`, image `0xe8000`, heap-top `0x284000` | section dump |
| stacks/tunables | `_rtk_init_stack` 0x10000, `_rtk_irq_stack`/`_rtk_exc_stack` 0x1000, `_rtk_tunables` 0x5b0 (hdr `0x00240301`) | section headers |

All-zero bootstrap translation means **the loader defines placement**: iBoot
copies the image, populates `_rtk_boot_l1`/`_rtk_page_tables`, then starts the
CPU. "Zero entry start" (W11 §3) is the image's *designed* entry once placed —
fatal only for an empty CPU, which is what W11 correctly refused.

K14 boot sequence (disasm of `AppleH11ANEInterface` 10.19.2, boot function
referencing the "Chinook bootup" os_log blobs, code `…95e9850–95e9988`):

1. `readReg(map, 0x1050000)` — read **RVBAR**; `tbnz bit0` → if set, **skip**
   (bit0 = already-booted/"selene released" latch — matches W8's live RVBAR
   read `0x1`).
2. compose `x21 = (FirmwareLoaded_prop & ~0x7f0000000000_07ff) |
   0x0081_0000_0000_0001` — for a boolean property this reduces to the
   **constant `0x0081_0000_0000_0001`** = the ASC boot-ROM entry, *not* an
   image address.
3. `writeReg(map, 0x1050000, x21)` — RVBAR write.
4. Cold/Warm boot via **`rANE_SCRATCH7` = 0 / 1** ("Writing 0 to
   rANE_SCRATCH7 to effect a Cold Boot" strings + `InitANEScratchRegisters`).
5. Boot args for the fw go through `SetupFWInitBootArgs(
   ANESharedMemorySurfaceParams*)` — a DART-mapped shared surface; a dev
   path (`ane_rtb_disable_fw_load` boot-arg, "copy custom FW to the right
   directory", vnode APIs) proves the kext can also place the image itself.

**Erratum carried forward**: RVBAR absolute = ANE base + 0x1050000 =
**`0x285050000`** (already corrected in the init-sequence receipt; the
`0x285105000` in the W3/assignment text and mined-receipt §2 is the same
arithmetic slip).

## 3. Mailbox / IRQ / memory evidence from ADT + kext (the assignment ask)

Parsed the raw j414c ADT (from `DeviceTree.j414cap.im4p`, lzfse payload,
LE-headered node/prop format, parses CLEAN to end) and re-checked the live
/proc/device-tree on jw14m2:

| source | ane0 datum |
| --- | --- |
| static ADT (both t6021 j414c **and** t6001 j316) | `ane,t8020`, reg = engine 0x840000000/0x2000000 + 2 pmgr, **one** interrupt (AIC 884), `iommu-parent` = mapper-ane0, **no** sram, **no** segment-ranges, **no** mboxes, **no** nub child |
| t6021 live DT (m1n1 FDT) | `apple,t6021-ane`, 9 power-domain phandles, 3 iommu phandles, `status=okay`, still 1 IRQ, no mboxes/memory-region |
| ADT RTKit template for comparison | IOPs are `iop,ascwrap-v4` with **4** interrupts (aop `[614 613 616 615]`, sio `[1249 1248 1251 1250]`) + asc/sram regs + `iop-*-nub` child — the shape kernel `apple-mailbox`/`apple-rtkit` binds to. **ANE has never had this node on any gen.** |
| iBoot | loads coprocessor fw from a fixed list (`ANE.img4`, `Ap,ANE1.img4`, …); the shipped j414c ADT memory-map is an empty template — iBoot populates load regions at boot, and m1n1 maps only sio/dcpext/isp (`dt_reserve_asc_firmware` reads `segment-ranges`, which ane0 lacks on both gens) |

**Design consequence (evidence-honest):** W11's §5 next-step (2) — a DT overlay
adding `mbox@285408000` (`apple,asc-mailbox-v4`, 4 IRQs) + `mboxes` +
`memory-region` + helper-compatible — **is not derivable from evidence**. The
ADT has no mailbox IRQs for ANE on t6021 (or t6001); any 4 numbers we typed
in would be invented. The H13 proof (t6001 ADT equally bare, yet Linux ANE
binds and runs inference on jw16) shows the ANE never used the kernel mailbox
binding. The only defensible Linux architecture is the kext's own: **single
IRQ (AIC 884) + in-window MBI registers (mailbox file at eng+0x1408000 —
read-proven live by W10 with FIFOCNT/WPTR/RPTR still at origin; doorbell
eng+0x1844000 — kext-pinned (W5), whose host WRITES SError'd in W5-live/W9
(partial write-grant wall, W9), so not safe until the fw-CPU contract is
proven — plus RTB/VERS eng+0x1840000) + CSNE_CMD fw-command protocol** —
exactly the driver lane's W4/W5
direction. `dma_alloc_coherent` + mapper-ane0 (dart-ane0, `dart,t8110`)
covers RTKit shared memory; no SART anywhere near ANE (nvme only).

## 5. What is still missing before a boot attempt (named, not guessed)

**Image placement for the ASC boot ROM.** The kext's RVBAR constant
(`0x0081_0000_0000_0001`) is a ROM entry, and the ROM needs the image (plus
boot args) at an iBoot-defined location. Neither the static ADT (memory-map
empty), nor m1n1 (doesn't process ane), nor the fw image itself (zeroed page
tables) carries it. Next lane: mine iBoot.j414c (extracted to
`/tmp/t6021-mine/iBoot.j414c.bin`, mBoot-20457.1.29, 0x256ab0 B) for the ANE
fw descriptor → load address; the `ANE.img4` string pool sits at 0x225519–
0x2255d9 with its loader table nearby; the kext's custom-FW vnode path is the
fallback oracle. Until that constant exists, any RVBAR/SCRATCH7 write would
be exactly the blind retry the lane rules forbid.
