## Defect 1 — macOS phandle byte-swap (data-correctness, published rows affected)

**Root cause:** `scripts/collect_macos.py` (v0.6.4, commit `112c32c4`)
decoded `AAPL,phandle` with `int.from_bytes(ph, "big")`
(collect_macos.py:106 in v0.6.4). macOS `ioreg` presents OSData
multi-byte cells in **host byte order** — little-endian on arm64. The
T6021 oracle: `AAPL,phandle = <69010000>` while IORegistry's own
`IOFunctionParent00000169` names the true phandle `0x169`; the
collector shipped `0x69010000`. Corroborating oracle: `reg` OSData is
u64-LE (address,size) pairs whose sizes match `IODeviceMemory` exactly
(`0x84000000/0x2000000, 0x8e080000/0x4034, 0x8e08c000/0x4000`), and
`IOInterruptSpecifiers <74030000>` = 0x374 = the AIC interrupt in the
receipt — every multi-byte cell on this path is host-endian.

**Which side was wrong: macOS only.** The Linux collector
(`collect_quick.py::_dt_u32s`) reads `/proc/device-tree` files, whose
bytes are DT-spec big-endian; `from_bytes(..., "big")` is correct
there. Live confirmation: all 9 Linux rows with phandle data in the
published dataset decode cleanly (no `0xXXXX0000` patterns, zero
unresolved `iommus_resolved`), while every macOS row with phandles was
swapped. Fix: read `"little"` on the macOS path, pinned by a fixture
rebuilt from the archived raw bytes.

## Defect 2 — pmgr reg capped at 64 bytes (data loss)

**Root cause:** the macOS probe's `_reg()` truncated any reg OSData to
64 bytes before hex-encoding (`truncated: ["reg_bytes:pmgr"]` in the
T6021 row). Reality: t6021 pmgr reg is **1168 bytes / 73 ranges** (raw
blob archived); t6002's is **3856 bytes / 241 ranges**. The field
exists to locate the ANE window and pre-plan the SET read-verify, so
the cap defeated its purpose exactly where it matters most. Fix: cap
raised to 4096 bytes / 256 ranges, ranges decoded to
`0xADDR/0xSIZE` (u64-LE pairs; u32-LE for 4/8-byte stragglers such as
mapper reg `<00000000>`), plus `reg_ranges_total` and explicit
`truncated[]` markers when anything is dropped. Linux path untouched.

## PROCESS DEFECT, named

create` publishes by default and I did not pass `--draft`, so v0.6.5
was user-visible while the decode legs were unresolved (the same
exposure as v0.6.3's first attempt). Both legs passed, so no unpublish
was needed, but the exposure was real. **Standing rule: create the
release as a DRAFT, gate the uploaded bytes, publish only after all
gates are green.**
