# 1x896 vs the exact 64-element program: the structural difference (2026-09-14)

Resolved model: `anthropic/claude-opus-5`, thinking high, not a fallback (lane `Ane1x896Diff`, session `01a0a054-e008-738b-95e9-c2e1e465e87a` model_change record at 2026-09-14T14:31:52Z; added by StatusDocSync from `history://Ane1x896Diff`).

## Verdict

`1x896` is not a shape problem. The named cause is a **124-byte task-descriptor
over-run declared in the ANEC header**: the exported bundle says its task
descriptor is `0x274` bytes when Apple's own object says the task stream is
`0x1f8` bytes. The driver hands that number to the engine as the task word
count, so the engine fetches 31 words past the end of the task and decodes the
CoreML weight-blob header — including a literal `0xDEADBEEF` — as register
writes. It never reaches a well-formed end of task, never signals TM idle, and
`readl_poll_timeout` returns `-ETIMEDOUT` (`-110`).

The defect is shape-independent and is present in every artifact of that
exported family, including the two 512-element bundles that were never
submitted. No hardware was touched for this analysis.

## The header and task-descriptor diff

Decoded `struct anec` (`patches/libane-ane.h:52`) plus the H13 register-record
walk of each task image:

| Field | 1x512 | **1x896** | 2048 | 64-el (proven) | parity-512 (proven) |
|---|---|---|---|---|---|
| `td_count` | 1 | 1 | 1 | 1 | 1 |
| `td_size` | 0x274 | **0x274** | 0x274 | 0x274 | 0x1f8 |
| `tsk_size` | 0x1f8 | **0x1f8** | 0x1f8 | 0x274 | 0x1f8 |
| `krn_size` | 0x400 | **0x700** | 0x1000 | 0 | 0x4000 |
| `src_count` / `dst_count` | 1 / 1 | **1 / 1** | 1 / 1 | 2 / 1 | 2 / 1 |
| `tiles` (×0x4000) | 0:1 4:2 5:2 | **0:1 4:4 5:4** | 0:1 4:8 5:8 | 0:1 4:1 5:1 6:1 | 0:2 4:2 5:2 6:2 |
| `nchw[in]` | 1,512,1,1,64,64 | **1,896,1,1,64,64** | 1,2048,1,1,64,64 | 1,64,1,1,64,64 | 1,512,1,1,64,64 |
| record stream ends at | 0x324 | **0x324** | 0x324 | 0x274 | 0x1f8 |
| terminates exactly at `td_size` | no | **no** | no | **yes** | **yes** |

Every task-descriptor register record is identical across 512, 896 and 2048.
The register images differ only in scalar magnitudes, all scaled exactly:

```
reg 0x00000[0], 0x00000[5]  element count   0x00010200 -> 0x00010380 -> 0x00010800
reg 0x13800 block            src bytes       0x400      -> 0x700      -> 0x1000
reg 0x17800 block            dst bytes       0x400      -> 0x700      -> 0x1000
reg 0x04800 block            const DMA       byte-identical in all three
reg 0x01f800 / 0x01f8c8      byte-identical in all three
DMA enables 0x13800/0x13804/0x17800  0x00033881 / 0x00033880 / 0x040000c1 in all three
```

So the 1x896 program carries no structural feature the 1x512 program lacks.
The `tiles[4] = tiles[5] = 4` entry is an honest round-up of a `896 * 64 =
57344`-byte span to `65536`; over-allocation is not the fault, and the decoded
corpus already covers 200- and 300-channel programs whose spans are likewise
not tile multiples.

## The named cause, in the bytes

Apple's Mach-O says the task stream is 504 bytes and the constants start at
+0x200 — identical for the 512- and 2048-channel objects:

```
model.hwx        __TEXT,__text   addr=0x30008000 size=0x1f8 (504)  fileoff=0x4000
                 __TEXT,__const  addr=0x30008200 size=0x400
model-2048.hwx   __TEXT,__text   addr=0x30008000 size=0x1f8 (504)  fileoff=0x4000
                 __TEXT,__const  addr=0x30008200 size=0x1000
```

The task's own register-record stream corroborates 504 exactly. Its last
record is the destination-DMA block, and it closes on the byte boundary:

```
@0x028 reg 0x01f800 x18   @0x074 reg 0x01f8c8 x12   @0x0a8 reg 0x000000 x16
@0x0ec reg 0x013800 x28   @0x160 reg 0x004800 x18   @0x1ac reg 0x008800 x4
@0x1c0 reg 0x00c800 x5    @0x1d8 reg 0x017800 x7  -> ends at 0x1f8
```

`tsk_size = 0x1f8` is therefore right, and the driver's kernel base lands
correctly on `__TEXT,__const`:

```c
/* omarchy-libane 80710786 ane/src/ane_drv.c:264 */
req.bar[KRN_BUF_BDX] = req.bar[CMD_BUF_BDX] + round_up(args->tsk_size, ANE_CMD_GRAN);
/* 0x1f8 rounded to 0x10 = 0x200 */
```

`td_size = 0x274` is wrong, and it is not read from the object. The converter
hardcodes it:

```python
# ane-linux-experiments tools/hwxv2-to-anec.py:11,243,246
TD_SIZE = 0x274
...
task_stream_size=text.size,   # 0x1f8, correct
td_size=TD_SIZE,              # 0x274, a constant
```

That number reaches the engine as a word count:

```c
/* ane/src/ane_tm.c:80 */
tq_write32(ane, TQ_SIZE1(qid), ((req->td_size >> 2) - 1) << 0x10);
/* shipped: (0x274>>2)-1 = 156  -> engine fetches 157 words = 628 bytes */
/* correct: (0x1f8>>2)-1 = 125  -> engine fetches 126 words = 504 bytes */
```

and libane copies exactly that many bytes into the channel the engine executes
from (`TQ_ADDR1 = btsp_iova`):

```c
/* patches/libane-ane.c:98 */
memcpy(nn->btsp_chan.map, nn->data, anec->td_size);   /* 628 bytes */
```

The 124 over-fetched bytes are the weight blob header, verbatim. For the 1x896
bundle, `cmd[0x200:0x280]` equals `weights.bin[0x00:0x80]` byte for byte
(the exporter writes a 0x40 header plus a 0x40 `0xDEADBEEF` blob record, payload
at 0x80). Walked as register records they are:

```
@0x200 0x00000001 -> "write 1 word at register byte address 0x1"
@0x240 0xdeadbeef -> "write 56 words at register byte address 0x2adbeef"
                     the highest register byte address in any of the five task
                     images inspected here is 0x1f8f4, so this is ~1400x out of
                     range, and the 56-word burst runs off the fetched task
```

The engine is left mid-burst on a nonexistent address, TM never reports idle,
and `ane_tm_get_status` (`ane_tm.c:100`, 1 s `readl_poll_timeout`) returns
`-ETIMEDOUT`. The observed failure was `ane_exec failed for program 0 with
result -1 errno=110` (`mlx-omarchy receipts/2026-09-13-jwm1-schema4-shape-aware-submit.json:34`).

## Why the 64-element program is immune

It is not immune because it is small. It is immune because its declared
`td_size` is the truth: `mil-hwx-compiler` sets `td_size == tsk_size == the real
task stream`, so the register-record walk terminates exactly at the declared
length. Both compiler artifacts satisfy that invariant; all four exported
artifacts violate it:

```
local h13-source-qualified 64-el   td_size=0x274 tsk_size=0x274  ends 0x274  exact=True
local h13-oracle-parity 512        td_size=0x1f8 tsk_size=0x1f8  ends 0x1f8  exact=True
ane-add-fp16-1x896                 td_size=0x274 tsk_size=0x1f8  ends 0x324  exact=False
ane-add-fp16-1x512                 td_size=0x274 tsk_size=0x1f8  ends 0x324  exact=False
ane-mul-fp16-1x512                 td_size=0x274 tsk_size=0x1f8  ends 0x324  exact=False
mil-oneop model-2048               td_size=0x274 tsk_size=0x1f8  ends 0x324  exact=False
```

Patching only the single header word `td_size` to `0x1f8` makes all four
terminate exactly, with no other change:

```
ane-add-fp16-1x896 (td_size=0x1f8)  ends 0x1f8  exact=True  TQ_SIZE1=125<<16
ane-add-fp16-1x512 (td_size=0x1f8)  ends 0x1f8  exact=True  TQ_SIZE1=125<<16
ane-mul-fp16-1x512 (td_size=0x1f8)  ends 0x1f8  exact=True  TQ_SIZE1=125<<16
mil-oneop 2048     (td_size=0x1f8)  ends 0x1f8  exact=True  TQ_SIZE1=125<<16
```

## The fix

`td_size` must be derived from the object, never from a constant. In
`tools/hwxv2-to-anec.py` (and the Mac-side `hwxv2-to-anec-patched.py` that
produced the shipped bundles), replace `td_size=TD_SIZE` with the first task's
actual size, which `find_task_offsets` already has in hand:

```python
td_size = (task_offsets[1] - task_offsets[0]) if len(task_offsets) > 1
          else (text.size - task_offsets[0])
```

The same constant is also used to slice the kdma window
(`tools/hwxv2-to-anec.py:222,235-238`); on a 504-byte task that read runs 124
bytes past `__TEXT,__text` too, and must use the derived size.

Acceptance test for the fix, hardware-free and already run above: for every
emitted ANEC, the H13 register-record walk over `data[0 : td_size]` must
terminate at exactly `td_size`. Both `mil-hwx-compiler` artifacts pass it
today; a corrected export must pass it before any submit.

## Second defect in the same family (not the hang)

Once `td_size` is corrected, the 1x896 bundle would still return wrong values.
The exported task's channel selector is the reverse of the ANEC/libane role
mapping:

```
words[8] = 0x00025864 -> src1 (0x13800) = channel 4
                         src2 (0x13804) = channel 1   (the kernel BAR, KRN_BUF_BDX = 1, legitimate)
                         dst  (0x17800) = channel 5

libane: dst_bdx = 4 + idx = 4 ;  src_bdx = 4 + dst_count + idx = 5
        (patches/libane-ane.c:35-36)
```

Both proven programs place the destination on channel 4 (`words[8] = 0x24966`
and `0x249a5`, dst = 4, sources on 5 and 6), matching libane. The export places
its destination on channel 5 and reads its input from channel 4, so the host
would feed the program's output tile and read back its input tile. The
underlying object agrees: its `__FVMLIB,__const` (input) sits *below*
`__FVMLIB,__data` (output), the reverse of the address order the decoded
matvec corpus uses. This is a correctness defect, not a timeout, and it is
also shape-independent.

## Practical route for a 896-element add today

`mil-hwx-compiler` already refuses the single-program 896 form and lowers it to
the proven class. Compiled here on this host:

```
add (1,512,1,1)  -> 1 program,  encoder h13-oracle-parity        (896 is not a covered channel count)
add (1,896,1,1)  -> 14 programs, encoder h13-source-qualified, 64 elements each
add (1,896)      -> 14 programs, identical
```

The decoded ALU parity envelope covers channel counts 64, 96, 200, 256, 300,
512, 768, 1024, 3072, 8192 and 16384 (`mil-hwx-compiler README.md:301-303`).
896 is outside it, so the in-repo path for a 896-element elementwise op is 14
of the exact 64-element programs — the only H13 program class with a device
receipt.

## Guarded execute: not attempted, and the procedure to run it

No execute was attempted. This analysis ran entirely on `omp-studio-local`
(x86_64), which has no ANE, and jwm1 was not touched: ownership of that host
was not granted for this slice.

The hypothesis is now named and cheap to falsify with one submit. Whoever holds
jwm1 should run exactly this, netconsole armed, `curl`-style wall-clock deadline
`<= 5 s`, stopping on the first `-110`:

1. Copy `ane-add-fp16-1x896`, write `0x000001f8` over the `td_size` field at
   file offset `0x08` of `model.anec` (leave every other byte alone), and
   re-stamp the bundle manifest's `anec` digest.
2. Submit once. Expect either exact completion, or a completion with the
   input/output surfaces transposed per the second defect above — both of which
   confirm the cause. A further `-110` refutes it.
3. Do not loop. Do not retry. Do not reboot, unload, or take the GPU lock.
