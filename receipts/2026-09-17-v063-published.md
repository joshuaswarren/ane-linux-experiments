## What changed vs the failed driver

- Wheel source: the GitHub release URL, downloaded and sha256-asserted
  (`dcb84f7b…`) on both hosts before any gate — gating the uploaded
  bytes, not a local copy.
- stdout: files everywhere (`packaging.log`, `decode.log`,
  `*.status`); no pipes that can SIGPIPE the driver mid-run.
- /tmp: cleaned (gate-owned scratch only, after a no-live-process
  check) and ≥3 GiB asserted before gating — jwm1, the 7.6 GiB tmpfs
  host, had exactly 3 GiB free after cleanup; the gate fit. The 4.8 GiB
  foreign `/tmp/swift-bin-aur` was left untouched, accounted for.
- Scratch: `trap` removes the gate's mktemp dir on any exit, so a
  killed run cannot orphan gigabytes again.
- Decode leg: dedicated `V063REL` venv (mlx-lm==0.31.3 + release wheel
  `--no-deps`), `HF_HUB_OFFLINE=1 MLX_DISABLE_COMPILE=1`, under
  `flock -w 900 /tmp/m1-gpu.lock` — never the ambient python.

One first-attempt red, environmental and driver-side, not product: the
driver initially saved the downloaded wheel as `wheel.whl`, and pip
refused it (`Invalid wheel filename (wrong number of parts)`), failing
the packaging gate in 5 s. Renaming the downloaded file to its canonical
wheel filename fixed it; the second run was green end to end on both
hosts. Explicitly: this was NOT an ENOSPC, NOT a decode skip, NOT a pin
mismatch.

`verify-release-assets.py v0.6.3` printed VERIFIED (exit 0) against the
uploaded assets; its first run correctly FAILED on a notes hash-pairing
ambiguity (`hash  name` column order vs its name-then-hash window),
fixed in the release notes — the gate catching that is the gate working.
