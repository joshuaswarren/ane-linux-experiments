# H14/T6021 W10 — the fw-first hypothesis is falsified at its premise: the ANE ASC CPU is **stopped** and its mailbox has never carried a message; the "firmware heartbeat" is a mirror of CNTVCT_EL0 (2026-09-19)

Verdict: **(b) NEGATIVE — clean, evidenced falsification**, with the i2a
receive path positively mapped as a by-product. The firmware never
responded to the host because **there is no firmware running**: the ANE
ASC's `CPU_CONTROL.RUN` bit is clear, `CPU_STATUS.STOPPED` is set, RVBAR
carries no entry address, and both mailbox FIFOs read
`ENABLE=1, EMPTY=1, FIFOCNT=0, WPTR=0, RPTR=0` — pointers still at the
origin, i.e. not one message has crossed in either direction since reset.

The whole run was **read-only on the receive side and took zero aborts**.
jw14m2-linux never rebooted: up 18 min, load 0.00, SError count 0.

## 1. The premise that failed

W6/W9 recorded "the RTBuddy/RTKit firmware is alive and emitting a
continuous type-0 i2a heartbeat (hi=0x0b, ~29 ticks/3 s)" at
`ANE+0x1170000/4`, and the driver header calls that pair the
`fw->host u64 message pair` (`ANE_MBI_MSG_I2A_LO/HI`).

That surface is **the 24 MHz architectural counter**, not a mailbox.

Arithmetic that prompted the test: W9 captured
`i2a=0x0000000bb53eb904` = 50 285 426 948 at kernel `t=2059.7 s`;
divided by the 24 MHz Apple timebase that is 2 095 s — box uptime plus
the usual pre-Linux offset. A message register does not do that.

Phase `tick` settled it against `CNTVCT_EL0` with no new addresses at
all. Over 32 samples spanning 2.4 s the **absolute** difference
`i2a - CNTVCT_EL0` is a constant **13–18 counts**:

```
offset i2a-cntvct: min=13 max=18 mean=15.8  spread=5 counts (0.21 us at 24MHz)
relative magnitude: offset/value = 7.21e-10
total_d_i2a=55258865   total_d_cnt=55258862   (3 counts in 55.2M = 0.054 ppm)
implied_uptime_s=915   (box uptime at that moment: 915 s)
```

The 0.21 µs spread is exactly the instruction gap between the `MRS
cntvct_el0` and the two 32-bit MMIO loads, which are not atomic with
each other. It is not merely phase-locked to the timebase — to within
7.2e-10 it **is** the timebase.

Correction to my own instrument: the probe's `tick.summary` line prints
`"phase_locked_to_cntvct":9` / `"verdict":"NOT_TIMEBASE_LOCKED"`. That
counter demanded exact per-interval equality of `d_i2a` and `d_cnt`,
which non-atomic sampling cannot deliver; it is a threshold artifact of
a too-strict test, not a finding. The load-bearing statistics are the
constant absolute offset and the 0.054 ppm aggregate drift above.

### Step 2 decode: fixed vs varying fields, 24 consecutive ticks

There is no message structure to decode. All 64 bits are one
monotonically incrementing timebase value:

- **Varying:** bits 31:0 (`i2a_lo`) — changes on *every* read, including
  eight back-to-back reads with no sleep (`burst` i=0..7 advanced 380,
  168, 332, 238, 322, 331, 190 counts). A message register holds still
  between messages; this one never holds still.
- **Slow-varying:** bits 63:32 (`i2a_hi`) — `0x00000006` across a 3-pass
  surface scan, `0x00000008` in run 1, `0x0000000b` in W9, `0x0000000a`
  in W6. This is the counter's high word, which increments once per
  ~179 s of uptime. The lane read those different values across
  different boots as "the firmware changed its message"; they are just
  different uptimes.
- **The "type-0" nibble is an artifact.** The RTKit type field is
  `GENMASK_ULL(59,52)` of msg0. For a counter that has not reached
  2^52, those bits are structurally zero and will stay zero for ~6 years
  of continuous uptime. Every sample decoded "type 0" because it could
  not decode as anything else.
- **The "~29 ticks/3 s" cadence is an artifact.** The driver's watch
  loop polled ~29 times in 3 s and observed a different value each time.
  That is a poll count, not a message count.

The firmware "asks for" nothing. It never spoke.

## 2. The i2a receive path, mapped (Step 1)

The ANE DT node carries no mailbox — `reg-names = engine, pmgr, set`,
one IRQ named `ane` — which is why the lane never found the receive
side. But every sibling ASC on this live SoC describes the convention:

```
/proc/device-tree/soc/mbox@2a2408000
  compatible      = apple,t6020-asc-mailbox  apple,asc-mailbox-v4
  reg             = 0x2a2408000  size 0x4000
  interrupt-names = send-empty send-not-empty recv-empty recv-not-empty
```

i.e. **mailbox = asc_base + 0x8000**. The ANE kext builds `0x1400044` /
`0x1400048` — the Apple ASC `+0x44/+0x48` pair — so ANE's ASC base is
`ANE+0x1400000` and its mailbox is `ANE+0x1408000` = `0x285408000`,
which matches the sibling naming (`…408000`) exactly.

Offsets are upstream, not guessed. Two independent sources agree:

- `drivers/soc/apple/mailbox.c` `apple_mbox_asc_hw` (sha256
  `6ac8541d…53bc`): `a2i_control 0x110`, `i2a_control 0x114`,
  `i2a_recv0 0x830`, `i2a_recv1 0x838`, `CONTROL_FULL BIT(16)`,
  `CONTROL_EMPTY BIT(17)`.
- m1n1 `proxyclient/m1n1/hw/asc.py` (sha256 `4ca10554…c0b5`)
  `ASCRegs`: `INBOX_CTRL 0x8110`, `OUTBOX_CTRL 0x8114`,
  `INBOX0/1 0x8800/0x8808`, `OUTBOX0/1 0x8830/0x8838`, and
  `R_MBOX_CTRL` = `FIFOCNT 23:20, OVERFLOW 18, EMPTY 17, FULL 16,
  RPTR 15:12, WPTR 11:8, ENABLE 0`.

## 3. Step 3: no legal response existed, and the gate fired

Step 3 was conditional on Step 2 yielding a coherent decode. It did not
— it falsified the message. Independently, the preferred action (a pure
FIFO pop on the receive side) is **illegal against an empty FIFO**:
upstream's receive loop is `while (!(i2a_control & EMPTY))`, and
`i2a_control` reads `EMPTY=1, FIFOCNT=0`. Popping would have been a read
of an undefined port, not a protocol response.

The probe self-gated rather than being talked out of it by hand:


**No a2i send was issued and no doorbell was rung this lane.** The W9

## 4. Why the fw-first hypothesis does not hold

The hypothesis was "the firmware owns the conversation and the host must
not speak first on a2i." Two of its three limbs are sound; the premise
is not.

- **Sound:** RTKit protocol really is IOP-first. In `apple-rtkit`, the
  host waits for the IOP's management HELLO and answers with
  HELLO_REPLY. Expecting the firmware to open is correct.
- **Sound:** the host had never mapped the receive direction. It hadn't
  — the real one is at `0x285408114`, and nothing in this lane had ever
  read it.
- **False premise:** "the firmware is alive." It is not running at all.
  `CPU_CONTROL.RUN = 0`, `CPU_STATUS.STOPPED = 1`, `RVBAR` entry address
  `0`. The evidence cited for firmware liveness — the continuous type-0
  i2a heartbeat — was a free-running clock mirror.

So the firmware cannot own a conversation it was never started for, and
it cannot be waiting for the host to stay quiet. The reason the a2i
sends abort is not that the host spoke out of turn. It is that
`+0x1850000`/`+0x1844000` are not the mailbox (the mailbox is at
`+0x1408110`/`+0x1408800`, reads a sane `0x00020001`, and has an
`ENABLE` bit already set), and there is no IOP running behind them to
consume anything written there.

This also retires the W9 open question. The SError on the send class was
never protocol-level rejection or a missing "MBI-class grant"; the lane
was doorbelling addresses that are not a mailbox on a co-processor that
is halted.

## 5. Next-best candidate

**Boot the ASC, then let the firmware open the conversation — which it
will, because that is the RTKit contract.** The fw-first intuition gets
its fair test only after the IOP is running. Concretely, the standard
Apple ASC bring-up, which `m1n1`'s `ASC.boot()` is three lines of:

1. Resolve and load the ANE RTKit firmware image through the ANE DART
   (`iommus` is present on the DT node), since RVBAR entry is `0` and no
   image is resident.
2. Program `RVBAR` (`0x285050000`) with the entry address | valid.
3. Set `CPU_CONTROL.RUN` (BIT 4) at `0x285400044`.
4. Poll `CPU_STATUS.STOPPED` (`0x285400048` bit 1) to clear, then poll
   `i2a_control` (`0x285408114`) for `EMPTY` to clear — the firmware's
   own HELLO should land in OUTBOX0/1 (`0x285408830`/`0x285408838`).
5. Only then reply, via INBOX0/1 (`0x285408800`/`0x285408808`), *not*
   via `+0x1850000`.

Step 3 is the first host write to the ASC block and is the natural next
device window. Worth noting before it is attempted: writing
`CPU_CONTROL.RUN` with no valid firmware behind `RVBAR` starts a CPU at
address 0, so the firmware-load step is a prerequisite, not an
optimisation.

Secondary candidate if the ASC refuses to start: `asc_flags40`
(`0x285400040`) reads `0x000a0000`, which is unexplained and worth
decoding against the `AKF`/`RTBuddy` block documentation before forcing
`RUN`.
