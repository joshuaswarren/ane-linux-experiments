# T6001 ANE task-manager MMIO offset

Date: 2026-09-13
Scope: offline source only. No SSH, insmod, reboot, or MMIO.

## Result

T6001 TM is **not** at Linux `engine+0x20000`.

m1n1 names TM at ADT range-0 base `+ 0x1c00000 + 0x24000`:

| Item | Value |
| --- | ---: |
| ADT `ane0` range 0 | `0x284000000 + 0x2000000` |
| TM base | `0x285c24000` (`+0x1c24000`) |
| TQ base | `0x285c25000` (`+0x1c25000`) |
| T8103-shaped engine slice | `0x285c04000 + 0x24000` |
| TM as `slice+0x20000` | `0x285c24000` |
| TM_TQ_EN | `0x285c2400c` |

Linux `ANE_TM_BASE=0x20000` is a T8103 fact about a **0x24000 slice**, not about offset `0x20000` from the ADT start. Cycle 8/10 aborted because the T6001 overlay maps the ADT start (`0x284000000+0x1800000`) and then reads `+0x20000` (`0x284020000`), which is not TM.

## Questions

### 1. Distinct TM/TQ offset for t6000/t6001?

Yes. m1n1: `ADT range0 + 0x1c24000` / `+ 0x1c25000`. ADT properties do not name TM/TQ. apple-knowledge `cabf98e2` does not either. Linux `ane_hw_t6000` only changes DART (`manual=false`); it does not change TM.

### 2. Does range 1 look like TM?

No. Live/static `ane0` range 1 is `0x28e080000+0xc02c`. That is the SoC PMGR window (`power-management@28e080000`, Linux size `0x4000`). Range 1 is `0xc02c`, so TM at `+0x20000` cannot live there. Do not map or probe it as TM.

`ane1` range 1 `0x28e680100+0x3f2c` is the same class (PMGR-east adjacent), not TM.

### 3. Clock or firmware-load on ane0?

**Clocks, yes. Firmware-load property, not on the static node.**

Static `arm-io/ane0`:

- `clock-ids = <0x13e 0x13f 0x140 0x141>`
- `clock-gates = <0x1cf>` (same cell as `power-gates`, PMGR `ANE-SYS-V`)
- `pmgr.clocks` includes `PLL_ANE0`
- no `firmware-name`, no `pre-loaded`

Live ADT (boot-modified) additionally has `pre-loaded=1`, `asc-dram-mask`, `segment-ranges`, `__TEXT;__DATA`. m1n1 `ANERegs` has ASC (`ASC_IO_RVBAR 0x1050000`) and RTKit GPIO acks at `VERS+0x48`. `t6001-j316c-ane.dtso` has no `clocks` and no firmware node.

Clock enable and ASC handshake remain open even with the correct TM base.

### 4. Smallest safe next MMIO

Do **not** repeat `engine+0x20000` on the current `0x284000000+0x1800000` map. That is the cycle-8 abort.

Do **not** read unsourced `engine+0`. m1n1's first named register in that window is `ANERegs.PMGR1` at `+0x738`, not an ID.

Do **not** touch range 1 (`0x28e080000`).

Two sourced probes, neither run here:

1. **In the already-mapped window** (cycle-10 power hold, `ps_ane_sys_cpu` ACTUAL `0xf`, readl only): `ANERegs.PMGR1` at `0x284000738`. Lowest named register. Distinguishes "start of ADT range 0 is real MMIO" from "first 24MB is a hole". Not TM.
2. **TM discriminator** (needs a new `0x24000` mapping first, no DART overlap): map `0x285c04000+0x24000`, then `readl TM_TQ_EN` at `0x285c2400c`. Optional ID/version in the same spirit: `ANERegs.VERS` at `0x285840000` (`ADT+0x1840000`), also outside the current trim.

Probe 2 is the one that tests the offset. Probe 1 is the smallest MMIO that does not require a DTS change.

## Boundary

No hardware access. No DTS/driver edit. Clock-ids `0x13e..0x141` are not name-resolved beyond `PLL_ANE0` existing in `pmgr.clocks`. m1n1 `ane.base_addr` is the ADT range-0 start (same pattern as other m1n1 `get_reg(0)` devices); the T8103 node/engine/DART deltas match that assumption exactly.
