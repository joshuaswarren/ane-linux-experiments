# T6001 TM / firmware handshake vs T8103

Date: 2026-09-13
Scope: host-only source. No SSH, jw16, execute, unload, reboot, or MMIO.

The T8103-exact 64-el schema-4 add-mul already submitted on bound
`285c04000.ane` / `/dev/accel/accel0`. Doorbell survived; `ane_tm_execute`
returned `-110`. This note names the remaining handshake. It does not
repeat that execute.

## Result

TM offset is closed. Firmware/SET power is not.

T6001 now uses the T8103-shaped engine slice, so Linux `ANE_TM_BASE 0x20000`
lands on real TM. The ABI1 submit wrote TQ, rang `TM_PUSH`, and lived.
`TM_STATUS` bit 0 never became idle inside 1 s (`readl_poll_timeout` →
`-ETIMEDOUT` / `-110`).

T8103 Linux raises `ps_ane_set1..5` before that poll. Those controllers
are the m1n1 ANE SET block. T6001 Linux never instantiates the matching
block, so the doorbell can hit TM while the execution partitions stay
gated.

## Sourced offsets

ADT range 0 = `0x284000000`. Engine slice = that plus `0x1c04000`.

| Name | T8103 | T6001 |
| --- | ---: | ---: |
| ADT range 0 | `0x26a000000` | `0x284000000` |
| Engine slice | `0x26bc04000+0x24000` | `0x285c04000+0x24000` |
| TM | `0x26bc24000` (`slice+0x20000`) | `0x285c24000` |
| TQ | `0x26bc25000` | `0x285c25000` |
| `TM_TQ_EN` | `+0xc` | `0x285c2400c` |
| `TM_PUSH` | `+0x8` | `0x285c24008` |
| `TM_COMMITTED` | `+0x44` | `0x285c24044` |
| `TM_STATUS` idle bit 0 | `+0x54` | `0x285c24054` |
| `TM_ERROR1..3` | `+0x58/5c/60` | `0x285c24058` |
| SET PMGR base (m1n1 `ps_map`) | `0x23b70c000` | `0x28e08c000` |
| Linux PMGR window | `0x23b700000+0x14000` | `0x28e080000+0x4000` |

`0x28e08c000` = die0 PMGR `+ 0xc000` = ADT ane0 range 1 `0x28e080000+0xc02c`
offset `0xc000`. It is inside that ADT range and outside the Linux `0x4000`
syscon. It is not TM. Range 1 as TM remains forbidden.

T6001 `ps_prores@c000` sits on `pmgr_south` (`0x28e680000+0xc000` =
`0x28e68c000`), not on die0 `0x28e08c000`. Do not treat those as the same
register.

## Handshake differences

### 1. SET power (load-bearing)

m1n1 `proxyclient/m1n1/fw/ane.py` `ANE.power_up` (after ADT power enable):

```text
ps_map["ane0"] = 0x028e08c000
for offset in range(0x0, 0x38, 0x8):
    write32(ps_base + offset, 0xf)   # TARGET active
tm.reset()
```

That is seven PMGR words at `+0x00, +0x08, …, +0x30`.

T8103 maps the same pattern onto named genpd:

| Offset from SET base | T8103 Linux | T6001 Linux |
| ---: | --- | --- |
| `+0x00` | `ps_ane_sys_cpu@c000` | missing (die0 PMGR ends at `+0x4000`) |
| `+0x08` | `ps_ane_base@c008` | missing |
| `+0x10` | `ps_ane_set1@c010` | missing |
| `+0x18` | `ps_ane_set2` | missing |
| `+0x20` | `ps_ane_set3` | missing |
| `+0x28` | `ps_ane_set4` | missing |
| `+0x30` | `ps_ane_set5` | missing |

T8103 `ane@26bc04000` `power-domains = <set1..set5>`. T6001 overlay
`power-domains = <&ps_ane_sys_cpu>` only (`t600x-pmgr.dtsi` `@268` / `@2c8`).

Typed T6001 PMGR has `ANE_SYS` `@0x268`, `ANE_SYS_CPU` `@0x2c8`, and
virtual `ANE-SYS-V` / `ANE-SYS-DART`. No `ANE_SET` / `ANE_BASE` names.
m1n1 still hard-codes the `0xc000` block for `ane0`.

`ane_tm.c` comment in m1n1: TQ_EN “reset with ANE_SET pds”. Linux
`ane_hw_t6000` only flips DART `manual=false`. It does not add SET
domains or a TM enable variant.

Cycle 10 already showed `ps_ane_sys_cpu@0x2c8 actual=0xf`. That is the
engine MMIO partition, not the SET execution partitions.

### 2. `TM_TQ_EN` mask (after SET)

| Path | Write |
| --- | --- |
| m1n1 `ANETaskManager.reset` | `TQ_EN = 0x3000` |
| Linux `ane_tm_enable` | `TQ_EN \|= 0x1000` |

IRQ enables match (`0x4000000`, `0x6`). Priority table matches
(`0x1,0x2,0x3,0x4,0x5,0x6,0x1e,0x1f`). Default `qid=4`, `nid=0x40`.
`TQ_SIZE1` encodings agree for `td_size=0x1f8` (`0x7d0000`).

m1n1 writes `0x3000` only after the SET `0xf` loop. Measuring `TQ_EN`
before SET power does not test execute.

### 3. Not the next probe

- Static tunables at ADT+`0x738`/`0x798`/`0x7f8` (`ANERegs.PMGR1..3`):
  T8103 Linux never writes them either and still executes.
- `ANERegs.VERS` `ADT+0x1840000` = `0x285840000`, GPIO acks `+0x48`,
  `ASC_IO_RVBAR` `ADT+0x1050000` = `0x285050000`: outside the `0x24000`
  slice. T8103 Linux also never maps ASC/RTKit.
- Live ADT `pre-loaded=1`, `__TEXT;__DATA`, `asc-dram-mask`: present;
  Linux has no firmware consumer. apple-knowledge `MacBookPro18,2.yaml`
  ane0 has `ane,t8020`, clocks `0x13e..0x141`, IRQ 770, power-gate 463,
  and no TM/TQ fields.

## One next probe

**Read-only SET0 at `0x28e08c000`.**

- `readl` only. Same class as cycle-10 `ps_ane_sys_cpu` ACTUAL.
- Do **not** write `0xf` (m1n1 `power_up`; cycle-5 PMGR writes reset).
- Do **not** treat range 1 as TM.
- Do **not** submit the add-mul again, unload, or reboot.
- Needs a new 4-byte map (or a grown die0 PMGR syscon). Not in
  `0x285c04000+0x24000`.

Look at bits `[7:4]` (ACTUAL) and `[3:0]` (TARGET), `PS_ACTIVE=0xf`.

| Read | Meaning |
| --- | --- |
| abort | `0xc000` not decoded; stop; do not retry as write |
| ACTUAL `0` | SET engines gated: explains doorbell-ok / `-110` |
| ACTUAL `0xf` | SET already on; then read already-mapped `TM_TQ_EN`
  `0x285c2400c` for `0x1000` vs `0x3000`, still no execute |
