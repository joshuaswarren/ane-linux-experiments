# T6021/h14g ANE oracle mints — three linear geometries, index-encoded payloads (2026-09-17)

Verdict: **MINTED (6+6).** Oracle bundles for oproj/mm1/mm2 were compiled by Apple's own
ANE compiler backend for both `TargetArchitecture=h14g` and `h13`, on **jw14m2 (T6021,
M2 Max)** and **macstudio (T6000-family, M1 Ultra)** — same macOS build (26.6.2 / 25G83),
same ANECompiler.framework **9.509.0** on both hosts. Payloads are **index-encoded**
(pair28 watermark), never uniform, so the emitted weight permutation is readable offline
from bytes with no device execution. Load-bearing findings:

1. **Raw `ANECCompile` refuses hand-authored matmul MIL — target-independently.** The
   2026-09-01 exporter boundary (2-D `[1,16]×[16,32]` refused) extends to our 3-D
   geometry: `program(1.3)` with `matmul(x = t1, y = t0, transpose_x = false,
   transpose_y = false)`, BLOBFILE weights (offset 64, exporter-identical construction):
   `ANECCompile=1 callback_status=1`, no `model.hwx`, but an **empty
   `model.hwx.additional_weights.bin`** appears (the compiler parses the BLOBFILE before
   rejecting the program). Refused identically for target `h13` **and** `h14g` on
   jw14m2 — the refusal is op/dialect-level, not target-level.
2. **Working route: ANEForge's Espresso e5rt compile path** (`aneforge._runtime.compile_check`):
   dlopens `/System/Library/PrivateFrameworks/Espresso.framework` and calls
   `e5rt_e5_compiler_compile` with
   `e5rt_e5_compiler_options_set_custom_ane_compiler_options(options, "TargetArchitecture=<arch>")`
   — Apple's compiler, compile-only (no device op). The accepted MIL spelling differs
   from the refused one: `matmul(transpose_x = bool(false), transpose_y = bool(true))`
   with the weight const stored **[N, K]** (ANEForge `@op("matmul")`/`linear` emitter,
   `_BUILD_INFO` coremlc 3520.4.1/3520.5.1, `func main<ios18>`).
3. **h14g ≡ h13, byte-identical, per geometry, per host** (`cmp` = 0 differing bytes;
   equal sha256) — on ANECompiler 9.509.0 the compiled linear program carries **no
   target-architecture divergence** for these geometries. Any t602x↔H13 difference for
   linear lives in firmware interpretation / load path, not in the compiled program bytes.
4. **The compiled program is host-flavored.** Identical MIL + identical weights
   (shas equal across hosts), identical 2320-byte length, yet **1324 of 2320 bytes
   differ** between macstudio- and jw14m2-hosted oproj `h14g` programs. Therefore the
   **jw14m2-hosted mints are the t6021 oracles of record**; macstudio's set is the
   cross-check that isolates host-flavoring from target-flavoring (which is zero).

## Payload encoding (pair28 watermark — non-uniform by construction)

Every adjacent fp16 PAIR carries the 28-bit source pair index:

```
even half bits = 0x0400 + (p & 0x3FFF)           # positive normal fp16 (0.25 .. ~4)
odd  half bits = 0x8400 + ((p >> 14) & 0x3FFF)   # negative normal fp16
readback: p = (even - 0x0400) | ((odd - 0x8400) << 14)
```

All bit patterns are finite, non-zero, non-subnormal fp16 (checked in the generator);
no canonicalization incentive. Verified byte-exact in the emitted `weights.bin` at
offset 0x80: `0004 0084 0104 0084 0204 0084 ...` (= 0x0400, 0x8400, 0x0401, 0x8401 …).
mm1/mm2 weights are byte-identical to each other **by construction** (same flat
watermark over 4,194,304 halves; the geometry lives in the MIL shape and program).

This directly answers the H13 lesson (four device-only bugs from permutation-invariant
uniform payloads): the permutation is now readable offline by decoding each emitted
weight position's watermark and diffing against the source index — the h14g plane maps
corresponding to `g_inv(P)` / `pi256` / mm2-plane can be derived on Linux from these
bytes alone.

## Artifact container — read before deriving

Each `cache_<arch>/com.apple.e5rt.e5bundlecache/25G83/<graph-hash>/<prog-hash>.bundle/H13D.bundle/`
contains **`H13D.e5` (2320 bytes, the compiled program)** and
`main/main_ane/model.anehash` (129 bytes). This is the **e5 bundlecache container**, NOT
the hwx/`.anec` container whose 2432-byte section header at bytes [8192, 10624) is our
H13 load-bearing constraint — that header constraint belongs to the hwx route, which
this compiler build refuses for matmul MIL. The offline h14g weight-map derivation
should parse `H13D.e5`'s DMA/task descriptors and correlate them against the
index-encoded `weights.bin` (both archived here). Note the bundle dir name says "H13D"
even for h14g targets — cosmetic on this build.

## TargetArchitecture classification (job 2) — settled

Chain of controlled experiments (all details + evidence in
`insurance/fixed-path-experiment/`):

1. Same host, same inputs, recompile at the SAME absolute path → **byte-identical**
   (0 differing bytes). The compile is deterministic given inputs+path.
2. The earlier "same-host churn" (1117 bytes between two macstudio runs) was
   **path-derived**: the MIL source path is embedded verbatim in the program
   (`input-file-path` metadata), and changing the path re-salts the encoding — program
   length tracks path length exactly (2320/2328/2344 bytes for 31/39/56-char paths).
3. Identical MIL + identical weights + **identical absolute path** on the two hosts →
   H13D.e5 (macstudio, M1 Ultra) vs H14C.e5 (jw14m2, M2 Max) differ by **exactly ONE
   byte, offset 2312 (0x908): value 2 vs 33** — a family/chip identifier field. The
   entire task-stream program is otherwise byte-identical.
4. Family selection is **local-hardware-keyed**: bundle dirs are named `H13D.bundle` on
   macstudio and `H14C.bundle` on jw14m2 regardless of whether `TargetArchitecture=h13`
   or `=h14g` was passed. The option does not steer the emitted family on this build.

**Verdict: Main's parsimonious inference is CONFIRMED.** `TargetArchitecture` is
ignored for family selection; oracles are host-SoC by construction (every H13 oracle we
own is M1-hosted; jw14m2's mints are the only t6021-family oracles). Operationally:

- The compiled linear program is **family-invariant apart from the one-byte id at
  0x908** — the H13 program format, and by byte-parity transitivity the H13-derived
  weight-plane maps, carry over to t6021/H14C program-side unchanged.
- Any t602x-specific ANE behavior lives in **firmware interpretation at load/exec
  time**, not in compiled program bytes — which is exactly where the Linux/m1n1 side
  must look next (SET window `0x8e08c000` read-verify on this machine).
- Minting rule going forward: **mint on the target SoC** (or accept the one-byte family
  id delta); do not trust `TargetArchitecture` to cross families on ANECompiler 9.509.0.

## Container warning (prominent, per Main)

These artifacts are **`e5bundlecache` containers** (`H13D.bundle`/`H14C.bundle` +
`*.e5` 2320-ish bytes + `model.anehash`), **NOT the hwx/`.anec` container**. The
load-bearing H13 constraint "2432-byte section header at bundle bytes [8192, 10624)"
DOES NOT APPLY to anything in this archive — that header belongs to the hwx route,
which ANECompiler 9.509.0 refuses for matmul MIL (see ADDENDUM 0 above and the main
receipt's refusal section). Reading hwx/.anec structure into these `.e5` bytes will
corrupt any derivation.
