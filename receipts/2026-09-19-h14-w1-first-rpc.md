## 3. What this does and does not prove

- **The fault is machine-level and independent of device contact — this instance had none.**
  The phase-1 model ("probe hung, box reset seconds later", ambiguous single instance) is now
  superseded: the same wedge→reset class killed the box while the only in-flight activity was
  an ssh exec that never reached sudo. Device-contact correlation from phase-1 is **weakened**;
  this is box hardware/firmware class (power/PMIC/board), as phase-1 concluded from the
  zero-contact deaths.
- The wedge signature is new evidence: sshd stopped servicing NEW sessions ~35 s before the
  reset while the kernel kept logging RX — userland partially wedged first, kernel alive,
  then below-kernel reset. On the next pass, an ssh-serviceability health gate
  (two consecutive short ssh round-trips ≥10 min apart post-boot) must pass BEFORE any
  `/dev/mem` work; a wedge observed at the gate means capture-and-stop without touching the device.
- The probe itself was never exercised in the field, so the per-address-flush fix remains
  validated only statically (it is `python3 -u` + per-address print, unchanged design).
- Nothing was retried after the death (STOP-capture-no-retry held; the only post-reboot ssh
  traffic was journal/pstore/netconsole reads and this receipt's bookkeeping).

## 4. W1-prep delivered: hello tool corrected (omarchy-ane `feat/t6021-rtkit-w2`)

Static cross-check of the staged `h14_rtkit_hello.py` against m1n1 `proxyclient/m1n1/hw/asc.py`
and Asahi `drivers/soc/apple/rtkit.c` (asahi branch) found the staged tool would have failed
silently on first contact:

1. **64-bit mailbox messages (fatal):** `INBOX0/OUTBOX0` (+0x8800/+0x8830) are `Register64`.
   The staged `recv()` read msg0 as u32 — MGMT type bits [59:52] live in the HIGH half, so
   HELLO would never match; staged `send()` wrote msg0 as u32 — HELLO_REPLY/EPMAP/STARTEP
   type bits truncated. Fixed: read/write both halves (`+0/+4`).
2. **FULL-wait around sends** (m1n1 `Mbox.send` waits on `INBOX_CTRL.FULL`; 1-deep FIFO must
   never be overwritten in-flight): added pre- and post-write waits.
3. **Full handshake** added per `rtkit.c`: after EPMAP LAST → STARTEP (`type 5 | ep<<32 |
   FLAG bit1`) only for fw-announced endpoints (system set 1/2/3/4/8/0xa; app set 1..6 per
   the W2 kext decode — the sets overlap numerically, the fw's EPMAP bitmap arbitrates);
   SET_IOP_PWR_STATE(6) from fw → ACK(7) echoing state[15:0]; `--set-ap-on` drives
   SET_AP_PWR_STATE(0xb) ON=0x20 after the AP ack. App-EP doorbells (ep 1..6) are decoded
   (W2 field layout) and **capture-only** — never acked.
4. Docstring's writes-performed section now states the exact write set (MGMT replies only).

Deliberately NOT attempted (zero speculative writes): syslog/crashlog/oslog buffer requests
are logged and left unanswered — honoring them requires a DART-mapped buffer, which W1 does
not have; CSNE_CMD_PING (0x11) on INIT needs the host→fw ring whose base negotiation is not
in the W2 tables (kext opens RTBuddyEndpoints whose embedded rings at obj+0x38 are
host-allocated and DMA-mapped at SetupEndpoints — the fw-learning step is the missing
decode, W3 scope). These stay walls until the box holds long enough to run.
